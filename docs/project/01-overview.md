# 01 — Project Overview

These are the owner's decisions. Proposals from the planning docs are not listed here unless the owner accepted them.

## Goal

An image generating and animating tool: an AI-powered, dynamic engine that creates images from instructions generated by an AI. The AI is tuned, and it generates the instructions for the image generating tool based on that tuning. The engine will be used in many places at the same time.

## The 3 scopes

1. **AI Instruction Generator ("AI Instructor")**: the current scope. It only outputs the instruction the Image Generator needs. In this phase it also plans and maps the animation. See [`02-ai-instructor-requirements.md`](02-ai-instructor-requirements.md).
2. **Image Generator**: creates the images from the AI Instructor's instructions.
3. **Animate the images**: connects the generated images and animates them. Generating animation code belongs here, not in Scope 1.

## What it will create

- Sprites, soil, bosses, jungle creatures, crafting things and crafting resources.
- It also decorates sprites that already exist, for example by changing a tree's appearance or adding small animations.
- Full sprite creation, including stats and rarity, happens in specific areas: boss fights, weapon crafting and other crafting.

The aim is to make the game feel **alive**. For example, a new event such as Christmas makes trees snowy, and every tree looks different. Bosses are auto-generated, so each one differs from the others.

## Tuning: what is fixed and what can change

- Tuning sets which properties are fixed and which can change. Example: a tree keeps the size it was given, while its texture, color and animation change dynamically.
- **Size is decided by developers per sprite.** It is not fixed for all trees. Generated images must fit a certain number of tiles (one tile or more), so developers say what size each sprite should be.
- Size can also change within a limit. Example: a tree growing from small to large, with its appearance changing too.
- Game assets must keep the same look and theme while still being dynamic.
- These are only examples. The game decides what can change and what stays static.

## Separate tool, results only

- The image generation tool runs **separately**, not inside the game.
- Only the results are sent to the game.
- Assets are generated early, then validated (manually or automatically), then integrated into the game automatically when their time comes. There is no live generation. This is what "time order" means in this project.

## Engine and graphics

- The tool is written in **C++** and must be extremely efficient and fast.
- The model may be heavy. Optimize **our own code** around it, instead of stripping the model down.
- The graphics engine is **2D** for now and may become 3D later. The AI only gives instructions to the graphics engine, so the AI does not need to care about 2D vs 3D.
- The goal is a **good** engine. The budget is not strictly zero and may change.

## Game status

- The game is not designed yet. The current focus is finishing the image generation tool.
- Unique per-user NFTs generated by the AI are a possibility. Whether it will be a Web3 game is undecided.
